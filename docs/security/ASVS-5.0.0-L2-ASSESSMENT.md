## What the application does and why

The deployed architecture is Astro static pages, TypeScript Netlify Functions, Supabase Auth/PostgreSQL/Realtime, Zod validation, Cloudflare Turnstile and a queued email integration. It is one company per database/deployment. It is not the older Cloudflare Workers/D1 design and is not a multi-tenant SaaS service.

| Boundary | Implemented control and justification | Evidence limit |
| --- | --- | --- |

Staging capture mode deliberately has different public submission budgets. |

## Findings and closure criteria

Priorities are work ordering, not CVSS scores. **P1** means resolve before accepting real client production data/releases. **P2** means planned hardening or an explicit, bounded architectural decision. No finding here asserts that an attacker has already exploited the system.

| Finding | Priority | Evidence / reason | Concrete closure |
| --- | --- | --- | --- |
| **F01 - Main release controls configured; owner review exception documented** | P1 baseline; main control closed for the agreed solo-owner model | The initial `main.protected=false` snapshot is preserved. The follow-up confirms two active main rulesets, both successful required checks, merged all-file CODEOWNERS and PR #18's recorded owner authorization. Saved settings screenshots establish the empty guard bypass and exact owner PR-only review exception. | Retain the independent guard with no bypass and the narrowly scoped owner exception. Contributor releases require the owner's review unless the owner deliberately uses that exception. Independent review of owner releases remains an accepted limitation; restore it when an eligible reviewer joins. A separate staging protection decision remains open. This release/SSDF finding is outside the normative ASVS matrix. |
| **F02 - Security-event coverage and log inventory are incomplete** | P1 | 16.1.1, 16.2.1, 16.2.3, 16.3.2, 16.3.3. The app logs unexpected failures and business changes, but returns authorization/validation/origin/CAPTCHA/rate denials without dedicated security events. | Add one bounded structured security logger with UTC time, request ID, route template, event/result and an approved pseudonymous actor identifier. Omit query strings, bodies, passwords, OTPs, secrets, raw provider errors and full tokens. Define destinations/ACL/retention/alerts; test both event emission and sensitive-data exclusion. |
| **F03 - Private search can put personal data in request URLs** | P2 | 14.2.1. Three owner feature modules build GET searches with `q`; names/emails can enter edge/provider access logs. The search helper's comment about no personal data in the URL does not prevent a network query string. | Move sensitive search text into a validated request body behind the same authorization/origin/header controls. Keep pagination/status semantics explicit and avoid sensitive browser-history or diagnostic URLs. Verify network URLs and logging behavior; do not just hide the address-bar value. |
| **F04 - Account/password/session management is incomplete for handoff** | P1 | 6.2.2, 6.2.3, 6.4.3, 7.1.2, 7.4.3, 7.5.2. No complete supported password change/reset or active-session review/revoke interface was found; parallel-session policy is undefined. A supervised lost-factor runbook exists but is not a drill. | Design a simple owner experience using managed Auth, current-factor/fresh reauthentication, MFA-preserving recovery and session revocation. Define allowed concurrent sessions, name a recovery deputy, and test password change, reset, lost factor and replay of old sessions with synthetic accounts. Do not weaken the MFA switch. |
| **F05 - Context-specific weak-password policy is absent** | P2 | 6.1.2, 6.2.11. No documented organization/product-name denylist or enforcement exists. Provider common/breached-password settings are also pending H01. | Approve the list and enforce it wherever passwords are provisioned/changed, without composition rules or silently truncating long passwords. Verify provider options/plan capability before selecting the mechanism. Keep real passwords out of diagnostics. |
| **F06 - Backup crypto lifecycle, stretching and upgrade path need work** | P2 | 11.1.1, 11.1.2, 11.2.2, 11.4.4. The current envelope uses strong authenticated encryption, but `scryptSync` relies on defaults N=16384,r=8,p=1 and the STDBK1 format has no encoded upgrade parameters. | Record key/algorithm/certificate custody and lifecycle. Benchmark an explicit current passphrase KDF configuration, for example scrypt N=131072,r=8,p=1 with adequate memory allowance, or equivalent reviewed settings. Introduce an authenticated bounded format version, preserve STDBK1 reads, and test legacy restore, bad parameters, wrong key and tampering. Random high-entropy operator keys remain required; this is not evidence that AES-GCM failed. |
| **F07 - Data-classification and retention policy is incomplete** | P1 | 14.1.1, 14.1.2. Public/private boundaries and lead anonymization exist, but no complete approved matrix covers tokens, Auth data, audit, email copies, logs, backups and provider retention/access. | Approve protection/retention/recipient requirements per data class. Verify scheduled anonymization, access/erasure handling, provider/log copies and deletion replay after restore. Record client ownership and maintenance responsibilities. |
| **F08 - Vulnerability remediation deadlines are undefined** | P2 | 15.1.1, 15.2.1. Weekly review, Dependabot and npm audit exist; there is no risk-based deadline policy or evidence of ongoing adherence. | Agree severity/exposure-based response times, emergency release ownership and exception tracking. Maintain full software/provider inventory and review dependency changes. A zero-advisory audit does not verify authorization, deployment or unknown vulnerabilities. |
| **F09 - Static, privileged backend service credentials** | P2 / design decision | 13.2.1, 13.2.2. Backend integrations use long-lived vendor API keys; the database credential has broad service-role privileges and bypasses RLS. API authorization mitigates this, but does not make the service principal least privileged. | Assess scoped service identities, shorter-lived credentials and a narrowly privileged database execution role where the provider supports them. If constraints require the current model, document its residual risk, strictly limit secret custody/preview access, test the API boundary and rotate/revoke on compromise. Risk acceptance does not convert a failed strict ASVS control into a pass. |
| **F10 - Managed host transparently redirects plain HTTP API requests** | P2 / platform limitation | 4.1.2. The sampled HTTP health API received a 301. Browser navigation redirects are appropriate; the stricter API requirement is to avoid hiding an insecure client behind a redirect. | Keep all API clients HTTPS-only. Determine whether the production edge can reject plain HTTP API requests instead of redirecting; otherwise record the managed-host limitation and residual risk. Never probe this by sending actual credentials over HTTP. |

H01 also contains an unresolved OAuth scope question: `signInWithPassword` uses the provider's first-party password grant. ASVS 10.4.4 prohibits password grants when an OAuth authorization server is assessed. The matrix does **not** claim this row passes or silently exclude it. Confirm the boundary/profile, review supported alternatives if necessary, and document any unresolved deviation. Do not replace the working sign-in with an unreviewed flow solely to obtain a green checklist.

## Retrospective STRIDE view

This is a retrospective threat-model summary, not a claim that formal STRIDE was performed before the original implementation.

| Threat class | Concrete VSS scenario | Existing defense / remaining work |
| --- | --- | --- |
| Spoofing | A password-only or recreated same-email account tries to open private records. | Validated UUID membership, AAL2 and live session; finish H01/H08 and F04. |
| Tampering | A contributor bypasses review, a caller changes a package price, or a backup file is altered. | Server-owned package snapshots, transactions and authenticated backup envelope; retain the F01 main controls/owner exception and complete F06. |
| Repudiation | A sequence of denied owner actions cannot be reconstructed. | Business audits/request IDs exist; F02/H07 add denial events, correlation and protected retention. |
| Information disclosure | Staff reads an owner-only privacy request, direct REST leaks records, or a search email reaches logs. | API role gate, grants/RLS, safe output/no-store; F03/F07 and H02/H07 remain. |
| Denial of service | Bots exhaust accepted writes, database work, email quota or Functions traffic. | CAPTCHA, atomic budgets, size/deadline/pagination limits and queued outbox; verify H04/H07 and provider limits. |
| Elevation of privilege | A user changes metadata to owner or steals a broad backend key. | Role is server-owned and mutable user metadata is ignored; complete secret custody and F09. |
