# VSS security boundaries — 1.6.0

This review maps the supplied attack-family list to the actual application. It is a source hardening release, not a penetration-test certificate or a promise to stop every attack. See `VERIFICATION.md` for executed checks and `../SECURITY-UPGRADE-1.6.0.md` for deployment prerequisites.

## System and trust boundaries

- One company per deployment/database. Staff share the company's lead inbox; owner adds website publishing and privacy powers. This is not a multi-tenant SaaS application.
- Public Astro pages and a publishable Supabase key are intentionally public. Visitors can read published content and public change metadata, not business tables or private signals.
- Netlify Functions validate public writes, verify staff identity and authorize every private operation. The server key bypasses RLS, so the API's role checks remain essential.
- Supabase validates Auth tokens. Approved staff are bound to immutable Auth UUIDs. Production adds TOTP, live-session checks, eight-hour absolute expiry and fifteen-minute idle expiry; direct private signal access also uses the production policy.
- PostgreSQL controls transactions, constraints, grants and RLS. Only service-role RPCs can write business records. SQL definer helpers stay private with fixed search paths and explicit execution grants.
- The classroom runtime is loopback-only, separate from hosted accounts, and rejected by hosted build preflight. It is never a production server.
- Registrar, GitHub, Netlify, Supabase, Turnstile, email and operator devices remain external trust dependencies. Their compromise cannot be repaired by a CSS change or an API filter.

## Attack coverage

| Attack family from the supplied list | Implemented boundary | Evidence and remaining operation |
| --- | --- | --- |
| Brute force, spraying, credential stuffing, bot login | Production requires TOTP; owner login sends a CAPTCHA token to Supabase. Public signup/anonymous login must be disabled in the provider. | Production-auth and MFA-flow regressions. Enable Turnstile in Supabase Auth itself and check its rate settings; a widget alone does not protect direct Auth requests. |
| Phishing, recovery abuse, stolen OTP | No public account creation or custom recovery API. Recovery is a verified operator procedure. | TOTP is not phishing-resistant and a stolen authenticator/device remains a risk. Use platform passkeys/security keys where available and individual administrator accounts. |
| JWT forgery, fixation, hijacking, stale tokens | Exact bearer validated by Auth before claims are read. UUID membership, verified email, no anonymous identity. Production verifies the underlying Auth session and last activity. | Real PostgreSQL revocation/expiry/recreation tests and altered-token API tests. Browser tokens remain JavaScript-readable in tab storage; strict CSP and safe text rendering reduce that exposure. |
| IDOR, privilege escalation, forced browsing, mass assignment | All `/api/admin/*` routes require staff; owner-only operations recheck owner role. Closed schemas, fixed allowed columns/statuses, SQL grants and service-only RPCs. | Route-guard, workflow and RLS suites. Changing a record UUID never changes the caller's role. A staff member is intentionally allowed the company's whole shared inbox. |
| Cross-tenant access | Each company/staging environment uses its own Supabase project and credentials. | There is no tenant selector or tenant isolation feature. Do not combine clients in one database without a separately designed and tested tenant model. |
| SQL/search injection, forged price, business ordering | Parameterized SQL/classroom queries, fixed PostgREST filters, bounded literal searches and closed DTOs. Package prices come from published server data. | Real PostgreSQL workflow/search tests. No client-controlled SQL, table/column names or arbitrary RPC routing. |
| NoSQL, LDAP/XPath/XML/XXE, SSTI, code/OS injection, unsafe deserialization | Those interpreters and public execution endpoints do not exist. Runtime input is bounded JSON validated before use. | Do not introduce `eval`, shell commands, XML parsing, dynamic templates, or user-selected file paths. Reassess when adding a feature; absence is not a generic sanitizer. |
| Prototype pollution | Validated schemas select known fields; published content has bounded typed structures; patched dependency graph. | Domain/content tests and source review. Review any future object merging or new dependency. |
| Stored/reflected/DOM XSS, HTML/CSS injection | User/CMS text uses text nodes and fixed safe renderers; no arbitrary CMS HTML. Build-generated CSP excludes inline script/eval and scopes Supabase connections to one project. | Existing DOM suites, built-HTML gates; added native malicious-message scenario still requires browser execution. Third-party CAPTCHA scripts remain a trusted dependency. |
| CSRF, CORS, clickjacking | Exact configured Origin for mutations, Fetch Metadata gate, explicit bearer headers, no credentialed cross-origin CORS, frame-ancestors none/X-Frame-Options DENY. | Request-hardening, origin and role regressions. No wildcard-origin fallback if the origin setting is missing. |
| Open redirect, browser messages, WebSocket misuse | API clients use internal paths and reject redirects; live subscriptions receive metadata only under RLS. No arbitrary cross-window message dispatcher. | Live-update/realtime-security tests. Test real hosted reconnect and offboarding before handoff. |
| Browser-storage exposure | Hosted auth uses sessionStorage with an in-memory fallback; previous persistent Auth entries are removed. Logout/role loss clears private UI and closes private updates. | Auth-storage, workspace and MFA-flow tests. A compromised page/device can still read an active token; use a future server-cookie architecture if that threat requires it. |
| SSRF, file inclusion, traversal, malicious uploads/parsers, Zip Slip | No upload/archive-extraction/file-fetch API. External service URLs are fixed/configured; redirects are rejected and fetches have deadlines. Asset choices use approved references. | Request/path and network-boundary tests. Development static fixture has real-path containment tests on Windows-style inputs. Hosting serves production assets. |
| Request smuggling/splitting, host/header injection, parameter pollution | Request guard rejects ambiguous CL/TE, unsupported encodings/methods, invalid paths, duplicate query keys and wrong production origins. Response fields/headers are fixed. | Request-hardening suite. Netlify's HTTP parser and network edge must also handle framing; an application guard is not a replacement for edge protection. |
| Cache poisoning/deception | Private/API responses declare browser and CDN no-store; owner route is no-store/noindex. Static HTML contains no private business data. | Header/build tests. Check emitted headers after every domain/provider cutover. |
| DoS, slow body, CPU/storage/email cost | Streaming byte limits, read/network deadlines, finite pagination/search/catalog size, CAPTCHA, HMAC IP/email buckets and global daily public-form budget. | Body-limit/CAPTCHA/budget tests with real PostgreSQL counters. Host firewall/quotas protect before Functions execute; free plans do not provide unlimited attack capacity. |
| ReDoS, decompression/XML bombs, expensive GraphQL | Input length bounds, simple fixed regexes, non-identity encoding rejected; no XML, decompression, public GraphQL or arbitrary query endpoint. | Input/request tests. A future search/query/parser feature needs its own complexity limit. |
| Race conditions, duplicate conversion/submission, price tampering | Atomic SQL RPCs, unique idempotency/source keys, server-owned package snapshot, revision conflict checks and leased bounded outbox. | Existing end-to-end database workflows and concurrent abuse-counter tests. Public retries require a new single-use CAPTCHA token; drafts keep their idempotency key. |
| Email/header injection, webhook forgery/replay | Server-owned recipient/sender, validated input, fixed provider transport; raw-body webhook signature/freshness verification and unique event IDs. | Existing notification/webhook/idempotency tests. Configure a verified sending domain and monitor bounces/delivery in the provider. |
| CSV/formula injection | No spreadsheet/CSV export endpoint. Database backups are privileged encrypted SQL, not spreadsheets. | If CSV is added, neutralize dangerous formula-leading values and test spreadsheet behavior before releasing it. |
| Vulnerable dependencies and supply chain | Patched happy-dom, fast-uri and undici; exact direct versions, final lockfile validation, audit CI gate, Dependabot and pinned official Actions commits. | Audit result is time-specific, not proof of no unknown flaws. Review updates, install-script changes and transitive advisories. |
| CI/cloud/repository takeover and exposed secrets | Minimal workflow permissions; generated-asset/source secret checks; no secrets in the ZIP. Ready-to-import main ruleset, real CODEOWNERS and separate private backup workflow. | Provider MFA, reviewer access, ruleset activation, secret rotation, deployment permissions and trusted-preview restrictions must be configured outside source. |
| Exposed DB/backup/debug tools | RLS plus table/function grants, private SQL helpers, source-only archive, production test-job routes disabled. Backups use authenticated encryption and omit sessions/staff approvals. | Real permission tests and backup tamper test. A restore needs new Auth bindings and a real restore drill. No live project Advisor was run here. |
| DNS/domain hijack, interception, crypto | HTTPS origins, HSTS without premature preload, secure random secrets, Supabase-managed Auth, AES-256-GCM/scrypt backups. | Registrar/client ownership, MFA, DNSSEC where supported, certificate/renewal checks and separate encryption-key custody are operational requirements. |
| Prompt injection, model poisoning/extraction, AI tool abuse | No AI model, agent, retrieval pipeline or AI tools are part of this website. | Not applicable to the present feature set. Do not route client records to a future AI feature without a new review. |

## Explicit limits

Production hardening requires the migration, `SECURE-PRODUCTION.sql`, real provider settings and the documented environment values. A ZIP cannot enable GitHub reviews, revoke a leaked provider key, change DNS or enroll the owner's authenticator. No production account or live database was changed while preparing this release.

Application submission budgets stop accepted writes within their ceilings; rejected traffic can still consume edge/Function resources. Provider outages, zero-days, phishing, malicious administrators and compromised endpoints remain risks. Account recovery and backup restore must be rehearsed by the named maintenance team. Do not publish real records until hosted acceptance and native browser tests pass.
