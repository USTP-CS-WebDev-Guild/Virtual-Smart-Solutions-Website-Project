# Deploy the complete system to your own accounts

Do this after the local walkthrough. This is the hosted version: public HTTPS pages, API, database, real sign-in, live events, owner editor, and scheduled jobs. It runs independently of your computer. You do not deploy `.local` or local logins.

Use your **team GitHub repository** with its isolated test Supabase project and Netlify site. Keep synthetic data. Free plans have limits; see COSTS.md. No Cloudflare or hosting CLI is required.

**Release 1.6.0:** this walkthrough configures staging. Existing installations and client production must follow [../SECURITY-UPGRADE-1.6.0.md](../SECURITY-UPGRADE-1.6.0.md), including the additive migration, UUID bindings, MFA policy and CAPTCHA. Do not reuse client production credentials in student previews.

## 1. Install the database once

1. Create your own Supabase Free project. Keep its database password private.
2. Open SQL Editor → New query. Paste the full contents of `backend/database/INSTALL-FRESH.sql` and run it once on this empty project. It installs all five canonical migrations together, including secure Realtime and identity/session controls. If it reports an existing application database, stop; use only the unapplied migrations for that project instead.
3. In Authentication settings disable new public signups. Create an owner user through Authentication → Users using your email and a unique password; confirm the email through the dashboard option/email flow appropriate to your project. No user signs up through this app.
4. Open `backend/database/owner-setup.sql.example`, replace the example UUID and email with that verified Auth user's exact values, and run it in SQL Editor. You need both a valid Auth user and an active UUID-bound owner row in `staff_users`. Never put a password into SQL or chat.
5. For another staff member, create/verify their Auth user, then explicitly approve their exact UUID and normalized email with role `staff` and `active=true`. Only trusted maintainers should get owner.
6. Get the project URL and **publishable key**, plus a separate **secret key**, from that project's API settings. The secret key is server-only. Use a password manager; do not paste keys into GitHub issues or support chats.

`INSTALL-FRESH.sql` is generated by `npm run db:prepare`; do not edit its copy separately. Start with no seeded records and test through the real forms.

## 2. Push source and import into Netlify

Follow REPOSITORY-SETUP.md. For the free classroom collaboration path, use a public source repository containing no secrets or records, and import it into Netlify. Current Free plans support public-repository contributors; organization-owned private repos/private contributor workflows can require Pro. Do not invite students as paid Netlify Developer seats; they contribute through GitHub. Keep **base directory empty/project root**; a website URL is not a directory.

Root `netlify.toml` supplies:

| Setting             | Value                                 |
| ------------------- | ------------------------------------- |
| Build command       | `npm run build`                       |
| Publish directory   | `dist`                                |
| Functions directory | `backend/functions`                   |
| Node version        | 24 LTS |

Get your generated address, for example `https://your-team-site.netlify.app`. You do not need a paid domain for testing.

## 3. Set hosting environment variables

| Variable                    | Your value                                                 | Availability                                      |
| --------------------------- | ---------------------------------------------------------- | ------------------------------------------------- |
| `APP_ENV`                  | `staging` for this synthetic-data team site                | Builds and Functions                              |
| `PUBLIC_SUPABASE_URL`       | Your project URL                                           | Build and Functions                               |
| `PUBLIC_SUPABASE_ANON_KEY`  | Your publishable key (or legacy anon key)                  | Build and Functions                               |
| `PUBLIC_TEST_ENVIRONMENT`   | `true`                                                     | Build and Functions                               |
| `PUBLIC_SITE_URL`           | Exact generated HTTPS site origin                          | Build                                             |
| `SUPABASE_URL`              | Same project URL as the public one                         | Functions only where scope controls are available |
| `SUPABASE_SERVICE_ROLE_KEY` | Your secret key (or legacy service-role key)               | Functions only where available                    |
| `APP_ORIGIN`                | Exact generated HTTPS site origin, no trailing slash/path  | Functions                                         |
| `RATE_LIMIT_SECRET`         | New private random value, at least 24 chars                | Functions                                         |
| `TEST_EMAIL_MODE`           | `capture`                                                  | Functions                                         |
| `OWNER_NOTIFY_EMAIL`        | `owner@example.test` for capture testing                   | Functions                                         |
| `RESEND_FROM`               | `Virtual Smart Solutions <hello@example.test>` for capture | Functions                                         |

Generate a rate-limit secret locally with `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`; store it privately. Do not expose it using `PUBLIC_`. Leave Resend secrets unset in capture mode. **Do not set `PUBLIC_CLASSROOM_MODE` on Netlify.** Build preflight rejects classroom mode or a private key in the browser-key variable. Private values must never go in frontend files, the repo, or netlify.toml.

Set Supabase Auth Site URL to the hosted origin and allow the approved localhost/test redirect URLs if you use email links. Trigger a redeploy after changing Netlify variables. Check logs: both API and scheduled-jobs Functions should deploy.

## 4. Make the public link public, keep owner data protected

In Netlify project configuration find Visitor access / Project visibility and set **Production → Public**. Provider labels may vary. This removes a _hosting_ login wall; it does not bypass the app's staff login. Source visibility is separate from visitor access. Check your hosting plan before connecting private/organization-owned source.

Open the actual published production URL in an incognito browser and a phone. A visitor should see public pages without Netlify login. Footer → Owner sign-in uses the Supabase Auth credentials you created, not the classroom passwords.

Run:

```powershell
npm run verify:deployment -- https://your-team-site.netlify.app
```

Replace the sample URL. The verifier checks public pages, database readiness, private API rejection, and anonymous WebSocket subscription/RLS. Then sign in as owner, click **Check contact form** and **Verify live delivery**, and complete TEST-THE-SYSTEM.md. The anonymous check alone cannot prove staff delivery.

## 5. Optional cloud development

For testing against your team's isolated Supabase project on your computer, run `npm run setup`, fill the ignored `.env` using `.env.example`, keep `APP_ORIGIN=http://127.0.0.1:4321`, and run:

```powershell
npm run doctor:cloud
npm run dev:cloud
```

Do not use a client production key for development. Default `npm run dev` continues to use the independent local classroom database even when `.env` has cloud keys.

## 6. Real client handoff

Use separate team staging and client production Supabase/Netlify projects, with the student tech lead and DevOps lead responsible for releases. Follow every production activation step in `../SECURITY-UPGRADE-1.6.0.md`: explicit verified UUID bindings, `SECURE-PRODUCTION.sql`, `APP_ENV=production`, `PUBLIC_TEST_ENVIRONMENT=false`, real hCaptcha/Supabase Auth configuration, fresh server secrets and actual owner MFA enrollment. Review business/privacy content, rehearse backup restore, and complete RELEASE_CHECKLIST.md. Changing only the test flag is insufficient.

Capture mode never sends mail. To enable real notices, configure Resend with a verified owned sending domain, sender, API key, webhook secret, and `/api/webhooks/resend`, then set `TEST_EMAIL_MODE=send`. Domain/provider charges and quotas are separate decisions. The owner inbox remains the source of truth if mail fails.

Published Netlify scheduled functions run maintenance; preview/local cloud testing has the owner **Run test jobs** tool. Deploy Previews need an explicitly approved origin and test credentials; never point student previews at real client data. Free hosting may pause at quota/inactivity limits; no plan here promises unlimited uptime at zero cost.

For staging/main releases without an instructor dependency, follow [STAGING-AND-PRODUCTION.md](STAGING-AND-PRODUCTION.md). For client launch use [DOMAIN-LAUNCH.md](DOMAIN-LAUNCH.md) and [MAINTENANCE-HANDOVER.md](MAINTENANCE-HANDOVER.md).
